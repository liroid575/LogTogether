# v0.15.0 — Reliability, groups, and recording polish

v0.15.0 is a family-testing reliability release. It keeps the Gold Day formula, mission-credit model, stable exercise IDs, local/offline storage model, and established private-data boundaries while strengthening installed-PWA onboarding, family authorization, notification reliability, comparison loading, completed-activity logging, and touch reordering.

## Cloud onboarding and account recovery

- Direct invite links continue to use opaque invite tokens as the preferred claim path.
- A newly installed PWA can recover eligible pending invitations from the authenticated user's verified email when browser-local invite state does not cross into the standalone iOS container. The query is bounded and cannot enumerate unrelated invitations.
- Existing Cloud reconnects persist their reconnect intent across reloads until active membership is confirmed.
- iPhone/iPad Google sign-in uses redirect-first handoff with auth observation established before redirect-result processing and bounded recovery if WebKit suspends or recreates the app process.
- The blocking sign-in overlay ends after Cloud authorization is proven; the larger profile/data reconciliation continues independently.

## Multi-group family authorization

- Ordinary members may belong to multiple groups through bounded `groupIds[]` membership.
- Legacy `groupId` remains the primary/backward-compatible value, so existing v0.14 single-group accounts continue to work.
- Ordinary-member visibility is granted only when active memberships overlap. The owner remains the administrator and `shareGroupIds` remains a separate owner-sharing concept.
- Group changes require owner-authorized mirrored access/member updates; members cannot add themselves to additional groups.
- Poke visibility follows the same family/group authorization model.

## Family Compare and weekly supplements

- Family Compare renders the first authorized snapshot before slower private hydration/supplement reconciliation finishes.
- Existing usable comparison data remains visible during background refresh instead of being replaced by an indefinite syncing state.
- Initial family loads and summary refreshes are bounded and become retryable on failure.
- Personal and Family weekly supplement details share one renderer/normalizer.
- Exact supplement-day documents remain owner-only. Family sharing uses bounded weekly detail containing date, local time, label, amount, and unit without exposing internal entry IDs or full ISO timestamps.
- Older aggregate-only weekly summaries remain readable; richer historical detail is not fabricated. A member's own current client must republish detail that did not previously exist in the shared summary.

## Gold Day and Pokes

- Gold Day scoring and the existing reward ledger/correction-debt model are unchanged.
- The signed-in user's private Poke wallet is observed in realtime, avoiding a race where the client could display an old balance before the asynchronous reward Function completed.
- Normal-user Poke caps, mute behavior, cooldown/flood controls, and server-side authorization remain in place.

## Notifications

- Deployment verification requires a valid client-visible VAPID public key. The VAPID private key remains server-side secret material.
- Notification onboarding/status checks no longer wait indefinitely for service-worker readiness.
- Current WebKit may subscribe through `window.pushManager`; older browsers retain the classic root service-worker PushManager fallback.
- Push payloads support Declarative Web Push while preserving the classic JavaScript notification handler for compatible older browsers.
- Service-worker precaching is best-effort so one transient asset failure cannot prevent worker activation.

## Exercise recording

- The exact 156 stable exercise IDs and 15 recording profiles remain the source of truth for live workouts and completed-activity logging.
- Completed-activity fields start blank instead of copying live starter targets into historical records.
- Effort defaults to **Not recorded**. Unknown effort remains unknown rather than silently becoming moderate-intensity guideline time.
- Whole-session duration is optional where the actual duration is unknown; LogTogether no longer invents duration/start time from repetitions and default rest.
- Existing non-sensitive tracker fields remain optional under **More tracker / device metrics** where relevant.
- No heart-rate history, HRV, VO2max, sleep/recovery, or wearable-calorie schema is added to family-readable workout data.
- Warrior I and Warrior II use per-side recording. Downward-facing Dog, Child's Pose, Cobra, and Sun Salutation remain non-sided.
- Gold Day and mission scoring are unchanged.

## Reordering and editor polish

- Permanent Up/Down controls are replaced with a dedicated drag handle plus an accessible **Move to position** fallback.
- The final touch implementation keeps the exercise DOM structurally fixed while dragging and chooses from deterministic insertion slots among exercise items only.
- Dragging is clamped to the first/last exercise, so an exercise cannot be moved below **Add exercise**, **Save changes**, or unrelated controls.
- iOS pointer-cancel, lost-capture, blur, and page-hide cleanup prevents orphaned drag UI.
- Compact controls, two-line exercise titles, viewport-safe position menus, and visible dividers improve mobile routine/circuit editing.

## Water and UI cleanup

- The redundant water-logged calendar dot is removed. Target-complete styling, selected-day state, supplement indicators, and perfect-month behavior remain.
- Empty Sports / Other is still hidden from the picker while legacy data remains readable.

## Security and privacy

- Firestore remains deny-by-default with server-enforced ownership, family identity, active membership, sharing, and group intersection checks.
- Pending-invite recovery is restricted to the authenticated verified email and a bounded query.
- Exact body metrics, hydration records, supplement-day documents, wallet data, precise GPX routes, and local media retain their established private boundaries.
- Browser Firebase configuration and the VAPID public key are client-visible by design and are not authorization secrets.
- The VAPID private key and administrative credentials must remain outside the repository.

## Compatibility and deployment

- Browser runtime dependencies remain at zero.
- Existing workout records keep their stored recording profile/version and are not reinterpreted by new defaults.
- `groupIds` is additive and old `groupId` remains compatible during the transition.
- v0.15 changes Hosting, Firestore Rules, Firestore indexes, and Cloud Functions relative to v0.14; deployments must therefore keep those surfaces compatible during rollout.
- Current service-worker cache marker: `logtogether-shell-v0.15.0-reorder-slots-hotfix10`.
- Live deployment verification retries briefly after a successful Hosting release to allow CDN propagation before reporting a version mismatch.

## Release gate

Before the final v0.15 tag, run:

- full unit/regression tests;
- Firestore emulator authorization tests;
- Functions syntax/reward tests;
- production dependency audits for root and Functions;
- private-config/deploy-config verification;
- clean Git diff/status checks;
- physical iPhone/iPad Home Screen tests for sign-in, invite recovery, notifications, Family Compare, and touch reordering;
- live post-deployment verification.
