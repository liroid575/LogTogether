# v0.15.0 — Reliability, groups, and recording polish

v0.15.0 focuses on family-testing reliability rather than changing LogTogether's game scoring. The Gold Day formula, mission-credit model, stable exercise IDs, local/offline storage model, and existing private-data boundaries remain intact.

## Invitations and installed PWA reliability

- Direct opaque QR invite codes remain the preferred claim path.
- A freshly installed PWA can recover a still-pending invitation after Google sign-in by querying only invitations addressed to that authenticated, verified email.
- The recovery query is constrained to `emailLower`, `status == pending`, and a maximum of three results. Multiple pending invitations are never guessed automatically; the user is asked to reopen the intended QR link.
- iPhone onboarding now states that the Home Screen web app has storage separate from Safari, so the invited Google account must sign in once inside the installed app.
- Installation remains a user-approved browser/OS action; LogTogether does not claim it can silently install itself.

## Poke wallet reliability

- The server-side Gold reward ledger, seven-Poke cap, deletion reconciliation, and correction-debt model are unchanged.
- The signed-in client now observes only its own private `pokeWallets/{uid}` document in real time. This removes the race where a one-shot read could happen before the asynchronous Gold reward Function finished its transaction.
- Push-notification availability remains independent from wallet credit.

## Multiple groups for normal members

- Ordinary members can belong to multiple Cloud groups through additive `groupIds[]` membership while the legacy/primary `groupId` remains for compatibility.
- Family visibility for ordinary members now uses group-set intersection. Owner sharing remains a separate `shareGroupIds` concept.
- Only the family owner can change another member's memberships, and mirrored `access` / family-member documents must change atomically.
- Existing v0.14 single-group accounts continue to work before the owner migrates them to the new array representation.
- Owner UI uses compact group chips plus an **Add to group…** dropdown instead of a checkbox matrix.

## Reordering and UI cleanup

- Circuit creation, saved-routine editing, and unstarted workout editing now use a Pointer Events drag interaction with a floating card, placeholder, neighboring-card movement, and edge scrolling.
- Permanent Up / Down buttons are removed.
- A compact `…` position chooser remains as the non-drag single-pointer alternative required for accessible reordering.
- `prefers-reduced-motion` suppresses reorder travel animation.
- The Water calendar no longer shows or explains a redundant “water logged” dot. Goal-hit and supplement indicators remain.

## Weekly supplements

- Personal and Family weekly supplement detail now share the same review-row renderer for date, local time, quantity/unit, total entries, days used, and Monday-to-Sunday recorded markers.
- Family detail still depends on the existing supplement-sharing preference and continues to use the bounded weekly aggregate rather than reading the owner's private supplement documents.

## Exercise recording and science audit

- The 156 stable exercise IDs and 15 recording profiles remain the source of truth for both live workouts and completed-activity logging.
- Manual completed-activity fields now start blank instead of copying live-workout starter targets into historical records.
- Effort defaults to **Not recorded**. Unknown cardio effort therefore remains unknown instead of being silently counted as moderate-intensity health-guideline time.
- For non-session records, whole-session duration is optional. If it is unknown, LogTogether no longer invents a start time from repetition count and default rest.
- Existing non-sensitive tracker fields can be entered under a collapsed **More tracker / device metrics** section (where applicable): speed, incline, machine resistance, laps, cadence, stroke rate, 500 m split, vertical gain, and pack weight.
- No heart-rate history, HRV, VO2max, sleep/recovery, or wearable-calorie fields are added to the family-readable workout schema in this release.
- Warrior I and Warrior II now use the same per-side recording rule as other clearly asymmetric mobility poses. Downward-facing Dog, Child's Pose, Cobra, and Sun Salutation remain non-sided.
- Gold Day and mission scoring are unchanged.

## Deployment and compatibility

- Browser runtime dependencies remain at zero.
- `groupIds` is additive; old `groupId` remains readable and writable during the transition.
- Existing workout records keep their stored recording profile/version and are not reinterpreted by new defaults.
- This release changes Hosting, Firestore Rules, Firestore indexes, and Cloud Functions, so all four surfaces must be deployed after tests pass.
- Service-worker cache: `logtogether-shell-v0.15.0-drag-cleanup-hotfix8`.

## Cloud reconnect hotfix

- Existing Cloud members now use a rule-complete grouped-member query that explicitly constrains `role == member`; Firestore Security Rules are not filters, so this avoids a query that can be rejected after the v0.15 group migration.
- A user-initiated Cloud reconnect survives a hard reload until active membership is confirmed.
- Concurrent Firebase Auth callbacks share one membership refresh instead of starting duplicate Cloud loads.
- The blocking Google sign-in overlay ends as soon as active Cloud authorization is proven; profile seeding and the larger data sync no longer keep users trapped on “Almost there…”.
- Cloud authorization reads have a 20-second UI timeout with an explicit **Retry Cloud connection** state; Local data remains untouched on failure.
- Service-worker cache bumped to `logtogether-shell-v0.15.0-auth-hotfix2` so installed PWAs receive the corrected client.

## iPhone / iPad OAuth-return hotfix

- iPhone and iPad now use Firebase Google **redirect** sign-in directly instead of trying popup first. Firebase documents redirect as the preferred mobile flow, and this avoids WebKit cases where Google authentication succeeds but the popup Promise never settles until the page is manually refreshed.
- The redirect-pending marker is mirrored to a short-lived local-storage marker containing only a timestamp, so an installed Home Screen app can finish auth after iOS suspends or recreates its web process. No identity, token, invite code, or health data is stored in this marker.
- Firebase's auth-state observer is attached before `getRedirectResult()` is consumed. Redirect-result completion is bounded; if WebKit delays it, LogTogether checks the already-persisted Firebase auth state rather than blocking forever.
- Returning to a still-open LogTogether window also probes the persisted Firebase user, and a 15-second watchdog turns an unresolved OAuth handoff into a retryable state rather than an infinite **Almost there…** modal.
- Android/desktop keep their existing popup-first behavior; only Apple mobile web contexts are routed directly through the full-page flow.

## Release gate

The candidate must not be deployed until all of the following pass from the real project checkout:

- production build and complete unit/regression suite;
- Firestore emulator authorization suite, including verified-email invite recovery and multi-group isolation;
- Cloud Functions reward tests;
- production dependency audits for root app and Functions;
- tracked-tree secret scan / private-config verification;
- deploy-config verification;
- physical iPhone test: QR in Safari → Add to Home Screen → installed PWA Google sign-in → invitation recovery → first sync;
- live post-deployment verification.

The source-backed research workbook is `docs/research/LogTogether_v0.15.0_exercise_and_reliability_audit.xlsx`.

## Family sync hotfix 3

- Family Compare no longer waits for the entire personal companion reconciliation before showing an already-authorized family snapshot. Weekly activity, calories, and water use the latest available family data while slower private hydration/supplement migration continues in the background.
- Initial family snapshot, family-summary publication, and post-publication refreshes are bounded at 20 seconds; failures become retryable errors instead of an unbounded “Syncing family progress…” state.
- Push/Poke status refresh no longer blocks family-companion completion; the private realtime Poke-wallet observer remains authoritative.
- Older weekly supplement summaries continue to show their aggregate totals, but now explain that date/time/amount detail can only be republished by that member’s own v0.15+ client. Other family members never gain access to the underlying private supplement-day documents.
- No Firestore Rules, Functions, scoring, or sharing-permission changes are introduced by this hotfix. Service-worker cache: `logtogether-shell-v0.15.0-push-hotfix6`.

## Notification hotfix 4

- Family notification onboarding/status checks no longer wait indefinitely for `navigator.serviceWorker.ready`; a missing/stalled active worker becomes a bounded retry state instead of hiding the prompt forever.
- Enable notifications begins permission/subscription work directly on the user gesture before UI rerendering, matching iOS/iPadOS Home Screen Web Push requirements more closely.
- Push setup may idempotently re-register `/sw.js` and waits at most six seconds for an active worker before returning a visible retry message. No Firestore Rules, Functions, sharing, or notification preference semantics changed.


## Deployment guardrail

- `verify:deploy-config` and `verify:live` now require a valid client-visible Web Push public key, so a release cannot pass verification while notification setup is unconfigured.


## Push reliability hotfix 6

- Modern WebKit uses standards-based `window.pushManager` when available, so subscribing on current iPhone/iPad Home Screen apps no longer depends on service-worker activation timing.
- Push payloads use the Declarative Web Push JSON format. New WebKit can display them without service-worker JavaScript; older browsers keep using the service-worker fallback.
- Service-worker precaching is best-effort, so a transient failure fetching one shell asset can no longer abort worker installation.
- Classic Push API browsers still use the root-scoped service worker. No notification preference, Firestore authorization, family visibility, or VAPID private-key boundary changed.
## Reorder interaction hotfix 7

- Touch reordering captures the pointer immediately and clears selection ranges so iPhone/iPad long-press text selection cannot compete with the drag gesture.
- The drag preview is now a compact movement label rather than a full cloned exercise form, reducing visual obstruction while moving long cards.
- Circuit and saved-routine edit controls use smaller top-right drag and destination buttons; the non-drag position chooser remains available for accessibility.
- This hotfix also updates the stale cache-name regression assertion that correctly failed when Push hotfix 6 changed the service-worker cache.
- No workout data format, scoring, Firestore authorization, or sharing boundary changes. Current cache: `logtogether-shell-v0.15.0-drag-cleanup-hotfix8`.
